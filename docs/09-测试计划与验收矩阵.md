## 0. 目的与使用方式

1. **验收口径唯一**：AC-01~AC-22 的全部断言以 [05 §4](./05-里程碑与验收.md#4-验收用例ac) 为业务定义、以 [07](./07-详细设计与接口契约.md) 为技术事实源、以本文为"落到哪个测试文件、什么 fixture、跑什么命令、断言什么"的执行手册。
2. **命名即契约**：实现者按本文的 `tests/...py::test_...` 命名；CI 与人工验收都按这些 node id 跑。若实际代码需要不同命名，先改本文 + 05，再改代码，不允许"代码有、文档无"。
3. **状态诚实**：`未跑` / `通过` / `失败` / `豁免` 四种状态，只有跑过才能写后三种；`豁免` 必须写原因与补偿手段，不得用"看起来对"代替运行。
4. **mock 优先**：所有自动化用例必须离线、确定性、可重复；live 模型只做**人工验收清单**（§5），不进 CI、不进 AC 自动断言。

### 1.3 组织与命名约定

- 文件名 = 被测模块（`test_gate.py` ↔ `engine/gate.py`）；e2e 文件 = 场景（`test_tdd.py`、`test_qa_fail.py`）。
- 用例名 = `test_<行为>_<条件>_<期望>`，一个 AC 至少一个**具名**用例；参数化用例用 `pytest.mark.parametrize` 且给出 `ids`（危险命令语料要有 id，失败时能定位到哪条）。
- 断言失败信息必须包含"期望 vs 实际"关键字段（如 `GateResult.reasons`），不要只断言 `not passed`。
- 同一 AC 允许多层覆盖（如 AC-05 unit 门控 + contract 退出码）；**只要有一层未过，该 AC 即未过**。
- 禁止：`time.sleep`、依赖真实网络、依赖系统时区/代码页、写死绝对路径、断言整段 Markdown 文本（用 `ArtifactStore.load` + 附录 JSON + hash 断言）。
- **实测基线（2026-10-30）**：`python -m pytest -q` → `378 passed`（261 个函数、参数化展开后 359 条）。

## 2. 公共 fixture 与环境

`tests/conftest.py` 已落地以下 fixture（实现者只用不改）：

| fixture | 作用域 | 提供什么 | 前置/行为 | 用于 |
|---|---|---|---|---|
| `platform_root` | session | 平台仓库根 `Path`，用于构造绝对路径、PYTHONPATH | 无 | 全部 |
| `demo_repo_src` | session | `fixtures/demo-repo`（只读）；不存在时 `pytest.skip("fixtures/demo-repo 尚未就绪")` | 由 T4 提供 fixture 仓库 | e2e |
| `repo` | function | `tmp_path/repo`，`fixtures/demo-repo` 的**可写副本**（不含 `.spec`） | `shutil.copytree` | e2e、contract |
| `settings` | function | 指向临时仓库的 `Settings`：`LLM_MODE=mock`、`PLATFORM_MODE=mock`、`SPECFLOW_OWNER=tester`、`LLM_CACHE=0` | `Settings.load(project_dir=repo, overrides=...)` | unit/e2e |
| `inited_repo` | function | 已执行 `specflow init` 的临时仓库（`.spec/` 五目录 + `state.json` + `AGENTS.md` + `hooks.json`） | 进程内 `cli.main(["init"])`，断言 exit 0 | 门控、hooks、e2e |
| `cli_call` | function | 进程内调用 `cli.main(argv, settings=...)` → `(exit_code, stdout)` | 依赖 `inited_repo` | CLI 级断言 |
| `hook_runner` | function | 真子进程 `python -m specflow hook <Event>`，自动补 `cwd/session_id/hook_event_name`，返回 `CompletedProcess` | 依赖 `inited_repo`；env 含 `PYTHONPATH`、`SPECFLOW_PROJECT_DIR`、`LLM_MODE=mock` | contract |
| `hook_json` | function | `hook_runner` + 解析 stdout JSON → `(payload, exit_code)` | 同上 | contract |

**环境变量基线**（`hook_env`）：`PYTHONPATH=<platform_root>`、`SPECFLOW_PROJECT_DIR=<repo>`、`LLM_MODE=mock`、`PLATFORM_MODE=mock`、`SPECFLOW_OWNER=tester`、`SPECFLOW_STRICT_HOOKS=0`；需要额外项时用 `extra_env` 叠加（如 `SPECFLOW_PLATFORM_FIXTURE=rpc-error`）。

**环境适配（Windows 沙箱实测，2026-10-30）**：沙箱下 0o700 目录不可访问 → conftest 统一 **mkdir mode 降级 + 独立 basetemp**；子进程统一 `encoding="utf-8", errors="replace"`；CLI 输出做 **GBK 兜底**（中文在 Windows 控制台不炸）。这三项是让 378 passed 可复现的前提，不改变任何断言口径。

## 3. 离线确定性策略

### 3.1 mock LLM：按 scenario 查表（ADR-004）

| scenario | 覆盖阶段/环节 | 关键内容 | 服务于 |
|---|---|---|---|
| `domain-input` | S0B | 术语/规则/反例 | AC-04 |
| `prd-input` | S1 | `requirements[]`（REQ-01…） | AC-05 前提、演示 |
| `explore` | S2 | modules/constraints/unknowns | 门控链路 |
| `tech-design` | S3 | options ≥2 / changes / risks ≥3（含 rollback） | AC-06/08/10 |
| `plan-task` | S4 | tasks：T1（test_first、≤4h、files） | AC-07、AC-15 |
| `archive` | S7 | rules_proposed（R-07/R-08） | AC-20 |
| `tdd-plan` | S5 Planner | steps 1..8 | AC-15/16 |
| `tdd-tests` | S5 Test Writer | 测试文件 + 用例数 | AC-15 |
| `tdd-impl`（`round=1`） | S5 Executor | **故意缺去重 + 空行处理** | AC-15/16 |
| `tdd-impl`（`round=2`） | S5 Executor | 修复实现 | AC-16 |
| `tdd-impl`（失败轮 1–4） | AC-17 专用用例 | 全失败脚本 | AC-17 |

约束：mock 响应必须能通过对应 schema（`mock.py` 返回前校验，失败直接抛以暴露 fixture 问题）；测试断言 `LLMResult.mode=="mock"`、`usage` 可有零值；**禁止**在测试里调真实 `LLMClient`。

### 3.2 socket 打桩（AC-21）

```python
def test_full_flow_offline_no_socket(inited_repo, monkeypatch):
    import socket

    def _blocked(*args, **kwargs):
        raise AssertionError("mock 模式下出现了网络连接")

    monkeypatch.setattr(socket, "socket", _blocked)
    # 之后跑完整 CLI 链路（run /prd-input … /archive），仍须全部成功
```

要点：打桩点在**测试进程**内（`cli_call` 走同进程）；`hook` 契约测试若需要"零网络"，则在 `hook_runner` 的 `extra_env` 中保持 `LLM_MODE=mock` 即可，不额外打桩子进程（子进程的网络由 mock 客户端自身保证）。

### 3.3 临时仓库副本（ADR-007）

- 每个用例用 `tmp_path` 下的 `repo`（`fixtures/demo-repo` 副本）；测试结束即销毁，**不写 `fixtures/demo-repo` 本体**。
- 需要 `.spec` 的用例在 `inited_repo` 上继续；需要"干净仓库"的用例直接用 `repo`。
- 手工演示只在 `.demo/<repo>` 副本里跑（[06 §1.1](./06-演示脚本与面试口径.md#11-准备与复位)）；`.demo/` 与 `.spec/` 均不进版本库。

### 3.4 时间 / hash / 随机

| 对象 | 策略 | 断言方式 |
|---|---|---|
| 时间戳 | `util.now_iso()` 统一入口；需要固定时 `monkeypatch.setattr("specflow.util.now_iso", lambda: "2026-10-30T20:14:03+08:00")` | 断言格式/顺序，不断言真实"现在" |
| hash | 只对**正文**（`---` 之后）算 sha256 前 12 位（ADR-006） | 改正文 → hash 变（AC-10）；只改 front-matter 时间 → hash 不变 |
| trace 文件名 | `today_stamp()` 生成 `hooks-YYYYMMDD.jsonl` | 用 glob 匹配 `hooks-*.jsonl`，不写死日期 |
| id 生成 | `util.new_artifact_id(prefix, existing)`、`ART-<STEM>-000N` | 断言格式与递增，不依赖 uuid |
| 随机 | 全项目禁用 `random` / `uuid`（08 §3） | 无需打桩；若发现随机即为缺陷 |

### 3.5 平台 fixture 注入

- 阶段参数：`specflow run "/qa-validate --fixture pipeline-fail"`（runner `args["fixture"]`）。
- 环境变量：`SPECFLOW_PLATFORM_FIXTURE=rpc-error`（`Settings.platform_fixture`）。
- 断言：`pipeline-fail` → `pipeline_status.status=="failed"` → `qa-report.verdict=fail`（AC-19）；`rpc-error` → `rpc_call.ok=false` → evidence `rpc=failed`。

### 3.6 子进程与编码

- 子进程一律 `subprocess.run([sys.executable, "-m", "specflow", ...], cwd=repo, env=hook_env(...), text=True, capture_output=True, timeout=...)`（08 §3.2）。
- 断言 stdout 为**单行**合法 JSON（`json.loads` 成功且 `\n` 不超过 1 个）；stderr 单行 ≤200 字（硬阻断场景）。
- Windows/macOS/Linux 一致：路径断言用 `Path.as_posix()`，中文用 UTF-8，不依赖系统代码页。
