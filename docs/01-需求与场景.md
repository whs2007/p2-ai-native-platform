## 1. 背景与痛点

把"一个需求从进门到上线"拆成阶段后，真正的问题不是"AI 不会写代码"，而是**每个阶段的输入输出没有契约**：AI 每次会话都从零理解仓库，阶段之间靠人脑串联，产物散落在对话里，出错只能靠"再问一遍"。

| # | 痛点 | 现状 | 后果 | 本平台的对应机制 |
|---|---|---|---|---|
| P1 | 上下文重复建设 | 每次新会话都要重新讲仓库结构、规范、术语 | 前 30% 的对话在重复劳动；不同会话结论不一致 | Day 0 准备层：`AGENTS.md` + `domain.md` + `templates/` + `index.md`，由 `SessionStart` 自动注入 |
| P2 | 阶段漂移 | 一句"帮我实现"直接跳到写代码，PRD/设计被跳过 | 需求理解错 → 返工；评审没有抓手 | 九阶段命令（S0A/S0B + S1–S7）+ 门控：缺少上游产物直接阻断 |
| P3 | 产物不可追溯 | PRD、方案、任务活在聊天记录里，代码里找不到出处 | 无法回答"这行为什么这么写"；新人无法接手 | 产物强制落盘到 `.spec/artifacts/`，`PostToolUse` 追踪产物与任务映射 |
| P4 | AI 破坏性操作 | 模型可能执行 `rm -rf`、`git reset --hard` 清理"碍事"的文件 | 未提交代码丢失，且无审计 | `PreToolUse` 在工具执行前按规则表（D/A/W/C）阻断，留 trace |
| P5 | 质量靠人盯 | 测试写完才补，或干脆不写；验证靠"看起来对" | 缺陷进入交付链路 | 多角色 TDD 闭环：Test Writer 先写测试，Verifier 依据测试结果判定，失败回流 |
| P6 | 经验不沉淀 | 踩过的坑只留在个人记忆里 | 同类问题下次重犯 | `/archive` 归档 + 规则回灌：新规则写回 `AGENTS.md`/模板 |

**一句话需求**：让"需求 → PRD → 方案 → 任务 → TDD 实现 → QA → 归档"成为一条**可执行、带人工门控、产物落盘**的流水线，而不是一次自由发挥的对话。

## 2. 三类角色

| 角色 | 是谁 | 核心诉求 | 在平台里做什么 | 关心哪个指标 |
|---|---|---|---|---|
| **执行工程师**（主要用户） | 接需求写代码的开发 | 少写重复上下文、少返工、下班前能交 | 跑 `/prd-input` → `/add`，在失败回流时决策 | 阶段耗时、TDD 轮次 |
| **评审者 / 技术负责人** | 看方案、拍板架构的人 | 方案能不能一眼看懂、能不能拒 | 在门控点执行 `specflow gate approve/reject`，看 `design.md` 选型与风险 | 门控通过率、被拒原因分布 |
| **新成员 / 后续 Agent** | 接手仓库的人或下一次会话 | 快速知道这仓库怎么跑、为什么这么设计 | 读 `index.md`、`AGENTS.md`、`.spec/artifacts/`；不直接产出 | 首次上手时间、索引命中率 |

> 角色不是身份系统：MVP 不实现 RBAC，只用 `--as` 参数记录门控操作人（写进 `state.json`），便于演示与追溯。
> 阻断式人门只有两个（[07 §0 ADR-009](./07-详细设计与接口契约.md#0-实现决策记录adr)）：`design`（进 S4 前）与 `agents-md`（回灌生效前）；S5 实现抽检、S6 交付确认是**非阻断建议项**。

## 3. 九阶段用户故事（S0A/S0B + S1–S7）

阶段 ID 与 `.spec/state.json` 的 `stage` 枚举一致（`S0A/S0B/S1…S7`），定义细节见 [07 §5.1](./07-详细设计与接口契约.md#51-skillsdirskillmd-front-matter唯一事实源)。

| 阶段 | 命令 | 用户故事 | 产物 | 完成定义（DoD） |
|---|---|---|---|---|
| S0A 准备 | `/project-init` | 作为工程师，我想让工具自动摸清仓库结构和命令，这样不必每次手写背景 | `AGENTS.md`、`templates/`、`repo-profile.md` | 画像含语言/包管理/测试命令/入口/规范文件；命令基线 ≥3；模板 ≥3 个 |
| S0B 准备 | `/domain-input` | 作为工程师，我想把业务域规则和术语一次讲清，让后续会话共享 | `domain.md`、`index.md` | 含术语表 ≥8 条、核心规则 ≥5 条、每条规则带反例（AC-04） |
| S1 PRD 输入 | `/prd-input` | 作为工程师，我想把 PRD（本地或 docs-shuttle）变成结构化产物 | `.spec/artifacts/prd.md` | 含需求条目编号、验收标准、范围外声明（附录 `requirements[]` 强校验） |
| S2 综合探索 | `/explore` | 作为工程师，我想让 AI 先读代码和依赖，再谈方案 | `.spec/artifacts/exploration.md` | 受影响模块清单 + 现状约束 + 未知项（附录 `unknowns[]`） |
| S3 技术方案 | `/tech-design` | 作为评审者，我想看到选型、接口、风险，并能一键打回 | `.spec/artifacts/design.md` | 选型 ≥2、改动含路径、风险 ≥3 且各含回滚；状态经人工门控 `design` |
| S4 任务拆解 | `/plan-task` | 作为工程师，我想把方案拆成可验收的原子任务 | `.spec/artifacts/tasks.md` | 每任务含文件范围、`test_first: true`、≤4h 预估、验收点 |
| S5 TDD 执行 | `/add` | 作为工程师，我想让多角色循环把任务实现并自证 | `tdd-plan.md`、`tdd-report.md`、代码 + 测试 | 测试先于实现；Verifier 判定 pass；超 3 轮转人工 |
| S6 QA 验证 | `/qa-validate` | 作为评审者，我想在合入前看到可复现的验证证据 | `.spec/artifacts/qa-report.md` | 单测 + mock pipeline + mock RPC 三段证据（附录 `evidence[]`） |
| S7 归档沉淀 | `/archive` | 作为团队，我想把本次变更变成可复用的知识 | `archive-record.md`、更新后的 `index.md`/`AGENTS.md` | 变更摘要 + 回灌规则（附录 `rules_proposed[]`）+ 索引刷新 |

> S0 是**一次建设、长期复用**（Day 0），S1–S7 是每次需求的**主链路**；S0 的产物会被 S1–S7 注入，S7 的结果又回流到 S0。

## 4. 现状 vs 目标

| 维度 | 现状（无平台） | 目标（本平台） |
|---|---|---|
| 会话起点 | 空上下文 + 人工口述背景 | `SessionStart` 注入基线规则 + 模板索引（硬预算 ≤900 tokens） |
| 阶段推进 | 靠人记流程，随时可跳 | 命令触发 + 门控校验，缺产物直接阻断（`requires` 声明于 `skills/*/SKILL.md`） |
| 需求来源 | 手动复制粘贴 PRD 片段 | `docs-shuttle` 下载/认领（MVP mock），产物结构化 |
| 设计评审 | 口头/IM 里说"可以" | `design.md` 状态机 + `gate approve` 留痕 |
| 实现方式 | 先写实现，测试事后补或不补 | Test Writer 先写测试，Verifier 依据测试通过率判定 |
| 失败处理 | 人工发现，重新描述问题 | Verifier 输出结构化失败项，回流 Planner 修订计划（轮次上限 3） |
| 产物归属 | 聊天记录 | `.spec/artifacts/*.md` + front-matter + `index.md` 索引 |
| 危险操作 | 无拦截 | `PreToolUse` 规则表（W/D/A/C 四类，D-01…D-12）判定 allow/ask/deny 并解释替代方案 |
| 知识沉淀 | 无 | `/archive` + 规则回灌 → `AGENTS.md` 下次自动生效 |

## 5. MVP 边界

| In（做） | Out（不做，附理由） |
|---|---|
| 9 条阶段命令（S0A/S0B + S1–S7），全部 mock 模式离线可跑 | 真实内网平台接入（IP/环境不可得） |
| 4 个 Hooks（SessionStart / UserPromptSubmit / PreToolUse / PostToolUse） | 宿主无关的自研 Agent Runtime（改造成本高于收益） |
| 多角色 TDD 循环（Planner/Test Writer/Executor/Verifier） | 并行多 Agent 抢占同一仓库（冲突成本高） |
| 门控：产物完整性 + 人工 approve/reject | 权限体系、审批流、多人协作锁 |
| 平台 mock：docs-shuttle / Feature / pipeline / rpc / SSO | CI 真实回调、真实 Staging 环境 |
| 规则回灌（`/archive` 写回 `AGENTS.md`） | 规则冲突自动合并（MVP 只追加 + 人工确认） |
| `specflow init / run / status / gate / hook / doctor / restore / unlock` 管理命令 | Web UI、看板、指标图表（P2 无前端） |

**硬约束**：单人实习作品集，工期 5~7 天；`LLM_MODE=mock` + `PLATFORM_MODE=mock` 时零网络依赖；零运行时第三方依赖（ADR-001）；不写业务代码之外的框架代码。

## 6. 成功指标

> **测量口径**：以下指标全部在 **mock 模式**（`LLM_MODE=mock`、`PLATFORM_MODE=mock`）下测量；**live 模式只做功能演示，不承诺时延/注入体积等指标**（ADR-011），live 口径见 [06 §1](./06-演示脚本与面试口径.md#1-演示脚本mock-与-live-两套时长)。**2026-10-30 实测**：全量 378 passed，AC-01~22 全过；mock 全流程 ≈7.5s；live（阿里云百炼 `qwen-plus`）全流程 145.74s、9 次调用（阶段 6 + TDD 3）、TDD 首轮 3/3、QA 三段 pass、回灌 R-06~R-08。

| # | 指标 | 口径 | 目标 | 测量方式 |
|---|---|---|---|---|
| M1 | 产物齐全率 | S1–S7 主链路应有产物中实际存在且 schema/附录校验通过的比例 | 100% | `specflow status --check` |
| M2 | 门控有效性 | 故意跳阶段（缺上游产物 / 人门未批）被阻断的用例通过率 | 100%（6/6） | AC-05…AC-10（[09](./09-测试计划与验收矩阵.md)） |
| M3 | 注入体积 | 单次 hook `additionalContext` 的估算 token | SessionStart ≤900、UserPromptSubmit ≤300（P95 不超预算） | hook trace 的 `context_tokens` |
| M4 | TDD 收敛 | mock fixture 任务集的 Verifier 首轮通过率 / 平均轮次（T1 固定 2 轮，AC-16） | ≥60% / ≤2.5 轮 | `tdd-report.md` 汇总 |
| M5 | 危险命令拦截 | 20 条危险样例拦截率、10 条白名单误伤率 | 100% / 0 | AC-12、AC-13 |
| M6 | 离线可跑 | mock 模式断网执行完整演示脚本，socket 连接数 | 0 网络请求、实测 ≈7.5s（目标 ≤90s） | AC-21（socket 打桩）+ `python scripts/demo.py --mode mock` |
| M7 | 回灌生效 | 新增规则后下一次 `SessionStart` 是否可见 | 1 次 `/archive` + `gate approve agents-md` 内生效 | AC-20 |

## 7. 风险与对策

| 风险 | 表现 | 对策（MVP 内可落地） |
|---|---|---|
| 阶段漂移 | 用户一句"直接实现"，AI 跳过设计与拆解 | 命令显式声明阶段；`UserPromptSubmit` 解析命令并按 `requires` 校验门控；`state.json` 记录当前阶段，越级直接 block（退出码 2） |
| 上下文注入膨胀 | 把 PRD/设计全文塞进每次会话，token 爆掉且注意力稀释 | 分层注入：SessionStart 只注入规则摘要 + 模板索引（≤900）；阶段产物只注入"摘要 + 锚点路径"（≤300），正文让模型按需读 |
| AI 改写产物不可控 | 模型"顺手优化"已批准的设计，导致实现与批准不一致 | 产物 front-matter 带 `status`/`version`/`hash`；已 `approved` 文件默认只读（写前校验 hash）；改写必须走"新版本 + 重新门控"（`gate revise`） |
| 依赖宿主 hooks 机制 | 换环境（Cursor/自研 Agent）hooks 不可用 | 协议层做成 stdin/stdout JSON 的独立可执行 `specflow hook <Event>`；宿主不可用时退化为 `specflow run "/<stage>"` 手动跑同样逻辑（ADR-005） |
| 演示形态弱（无 UI） | 面试现场不如网页直观 | 全程用文件 diff + `status` 表格说话；预置 fixture 与录屏；15 秒的 `PreToolUse` 阻断做开场 |
| 收益难量化 | "到底提升了什么" | 只用可测的 M1/M3/M4/M7，不吹工时百分比 |
| 与 P1 口径混淆 | 两段经历同期，容易被质疑 | 明确 P1 = 业务 Agent Runtime，P2 = 研发流程工程化；共享的只有"工具治理/上下文工程"方法论 |

## 8. 术语表

| 术语 | 定义 |
|---|---|
| **Day 0 准备层** | `/project-init` + `/domain-input` 的一次性建设，产出基线规则与领域知识 |
| **阶段（Stage）** | 主链路中的一个可命令触发的处理单元，S0A/S0B + S1–S7，有输入契约、产物契约、门控；定义在 `skills/<stage>/SKILL.md` |
| **机器门** | 进入下一阶段的前置条件：产物存在性 + front-matter 状态 + schema/附录校验 + hash 一致性 |
| **人门（Human Gate）** | 阻断式人工审批，仅 `design` 与 `agents-md` 两处；S5/S6 为建议评审，不阻断 |
| **产物（Artifact）** | 落盘到 `.spec/artifacts/` 的 Markdown，带 front-matter，是阶段间唯一可信输入 |
| **Spec 驱动** | 以文件化规范（`AGENTS.md`/`domain.md`/产物）为唯一事实源，而非对话记忆 |
| **Skill** | 阶段对应的提示词 + 契约包（`skills/<stage>/SKILL.md`），声明输入、输出、门控与失败处理 |
| **Hook** | 宿主在固定时机调用的外部命令，用 stdin/stdout JSON 交换决策 |
| **Hooks Runtime** | 4 个 hook + 分发器 + 协议 + 降级策略的整体，负责注入、阻断、追踪 |
| **注入上下文（additionalContext）** | hook 返回给模型的文本，只允许摘要 + 索引 + 锚点路径，禁止全文 |
| **回灌（Feedback Loop）** | `/archive` 把新规则/新模式写回准备层，使下一次会话自动生效 |
| **Mock 模式** | `LLM_MODE=mock`（或 `auto` 且无 Key）+ `PLATFORM_MODE=mock`，模型响应查表、平台能力由本地 JSON fixture 提供，零网络 |
| **Trace** | `.spec/traces/hooks-YYYYMMDD.jsonl`，每次 hook 调用的入参、决策、耗时、token 估算 |
