# 拜访域知识（visit domain）

> 版本：v1 ｜ 来源：业务访谈 + `docs/prd/visit-import.md` ｜ 维护：retail-tools

## 1 业务域全景

BD（商务拓展）每天按门店清单执行拜访，主链路是：

```text
计划（Plan） → 签到（Check-in） → 日志（Visit Log） → 总结（Review）
```

- 计划：由主管或导入工具生成，描述「谁在哪一天拜访哪家门店」。
- 签到/签退：记录实际到店时间，是考核与结算的依据。
- 日志：拜访过程中的记录（陈列、库存、竞品）。
- 总结：日报/周报，由记录聚合而来。

数据来源有两类：POI 主数据（门店编码、名称、区域）和外部导入（CSV/Excel，
本需求只做 CSV）。导入是「计划」的主要生成方式之一，因此导入的正确性直接影响
下游签到与日报。

## 2 核心规则

| 编号 | 规则 | 反例（违反即错） |
|---|---|---|
| DR-01 | 一个门店一天只能有一条生效拜访计划 | 同店同日两条计划都生效，签到记录归属不明 |
| DR-02 | 门店编码唯一，导入按 `store_code` 去重且保留首次出现 | 同编码两条都保留，或后出现的覆盖先出现的 `owner` |
| DR-03 | 计划日期必须是合法 ISO 日期（`YYYY-MM-DD`） | `plan_date=2026-13-01` 被当字符串放行，下游无法排序 |
| DR-04 | 门店名称只用于展示，不能作为匹配键 | 用 `store_name` 去重，把同名不同店（两家「望京门店」）合并 |
| DR-05 | 导入必须有显式表头，缺列即失败 | 无表头 CSV 按列位置猜字段，把 `owner` 塞进 `plan_date` |

补充说明：

- 规则 DR-01 的判定在「生效」维度，草稿/作废计划不参与冲突判断。
- 规则 DR-02 的「首次出现」指文件行序，不是按日期或编码排序。
- 规则 DR-05 的报错必须能定位到具体缺失列，便于 BD 修表头后重试。

## 3 术语表

| 术语 | 含义 | 易混项 |
|---|---|---|
| 拜访计划（Plan） | 待执行的一次拜访任务：门店 + 日期 + 归属人 | ≠ 拜访记录（已发生） |
| 拜访记录（Visit Record） | 已发生的签到/签退/日志事实 | ≠ 拜访计划（待执行） |
| 门店编码（store_code） | 外部 POI 的唯一键，导入去重依据 | ≠ 内部门店 ID（自增主键） |
| 门店名称（store_name） | 门店展示名，可能重名 | 不可作为匹配键 |
| 计划日期（plan_date） | 计划拜访发生的自然日 | ≠ 签到时间（含时分秒） |
| 归属人（owner） | 计划负责的 BD 账号 | ≠ 门店负责人（店长） |
| POI | 门店主数据系统，提供编码/名称/区域 | ≠ 内部 CRM |
| CSV 导入 | 按固定表头批量生成计划的能力 | ≠ Excel 导入（本期范围外） |

## 4 边界与禁区

- 不修改计费相关字段（`billing_*`），导入流程只读它们。
- 不直连生产库；演示与测试一律用 CSV 文件 + mock 平台。
- 不在导入阶段做门店编码合法性校验（外部 POI 负责），避免双重口径。
- 脏数据不静默丢弃：跳过空行可以，但格式错误必须抛错并保留原始行号。
